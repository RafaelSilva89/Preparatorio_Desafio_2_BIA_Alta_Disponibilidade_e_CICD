Aula 01: Apresentação do Novo Módulo

Born, pessoal, com esse módulo, eu tenho como objetivo cobrir os principais modelos de conectividade e todo o processo de segurança envolvido nessas operações para nos conectarmos ao nosso EC2, ao nosso banco ou algum outro serviço que envolva algum redirecionamento de porta na nuvem.

O meu grande objetivo é passar por todas essas etapas, começando pela forma mais simples, que é quando você lança um EC2, lança um RDS e se conecta diretamente nele. Sabemos já que essa não é a forma mais segura, é a forma mais simples e, provavelmente, é como muitos começam, se conectando diretamente no seu recurso.

Subnet B: Subnet adicional provisionada dentro da VPC (atualmente vazia no desenho, conforme o rascunho em vídeo).

Aula 07: SSM: Conceito + vantagens + montagem de ambiente em subnet pública e privada

Após já termos explicado todo o processo que envolve baixo host, utilizando SSH, utilizado o Instance Connect para jogar uma chave PM temporária, agora vamos falar de um serviço que eu acho que é uma grande virada quando falamos sobre segurança para esse modelo de conexão na AWS, que é o SSM.

Trabalhando no modelo público, que foi a primeira aula que fizemos desse modelo de conectividade, parecia o melhor modelo, mas nós avançamos, mostramos o processo do baixo host e como ele traz inúmeros benefícios, agora vamos mostrar que o nosso modelo de baixo host com SSH, de certa forma, fica para trás no quesito segurança quando a gente coloca o SSM na jogada.

PM = porteiro moderno
Nesse PM também tem um Security Group, mas apenas para controle das entradas nas instâncias que queremos nos comunicar.

Nesse tipo de conexão nenhuma regra de entrada precisa e aqui é a grande vantagem é um processo de autorização que acontece através de IAM, então aqui nosso controle de segurança acontece através do IAM, existem inúmeras vantagens desse processo, o primeiro deles é a centralização, a gente não precisa aqui de chave PM, nem chave fixa, nem chave temporária, onde o EC2 Instance Connect era uma alternativa, a gente faz o processo de controle de acesso apenas por IAM, então o nosso IAM vai precisar ter permissões que autorizem, a nossa EC2 vai precisar de um Instance Profile que permita que um serviço que tem nela chamado Agente do SSM possa operar e
permitir a comunicação do nosso usuário, esse cara (PM) aqui por não ter precisado de nenhuma regra de entrada, ele precisa se comunicar com a internet para que a
comunicação aconteça.

O SSM é um serviço da AWS e dentro do EC2 temos um agente, algumas instâncias da AWS já têm esse agente pré-instalado para você simplesmente utilizar, basta que a gente configura as permissões e IAM, a Role para essa EC2, permitir que esse cara consiga fazer a comunicação com o serviço da AWS.

O Fluxo de comunicação:
Nosso usuário vai iniciar o processo com permissões de IAM através do Cli da nossa máquina, quando acontece esse fluxo, a gente vai passar o ID da instância, então ele vai saber que se trata dessa instância e o processo de comunicação vai partir do agente, ou seja, se parte do agente eu não estou batendo direto no agente, o tráfego é de outbound, não inbound.

Outbound, pessoal, por padrão é o tráfego que que sai da instancia, deixamos abertos (0.0.0.0/0). A gente deixa aberto, então com isso o tráfego de saída da instância está livre para a internet, então com isso ele consegue se comunicar com o serviço do SSM e a partir daí a comunicação consegue ser estabelecida. Então esse cara aqui não precisa ter entrada e não precisa ter nenhum tráfego de entrada, mas ele precisa conseguir sair para a internet, esse é o grande detalhe, esse cara precisa conseguir sair para a internet, ou seja, existem duas forma de sair para internet.

- Uma delas é esse agente estar em uma subnet pública.
- É ele estando em uma subnet privada, mas tendo saída para a internet, usando NAT Gateway na subnet pública e configurando rota de saída por aqui, então o tráfego vai sair para internet.

Para esse ambiente nós vamos precisar de dois security groups:
	- um security group para subnet pública
	- outro security group para subnet privada

💡 Por que sudo su - ec2-user e não trabalhar onde você caiu:

/usr/bin é reservado aos executáveis do sistema operacional e ao gerenciador de pacotes. Misturar código de aplicação ali gera conflito — uma atualização do SO pode sobrescrever arquivos.
Escrever nessas pastas exige root, e rodar aplicação como root é uma falha grave de segurança.
ec2-user é o usuário padrão do Amazon Linux. Em /home/ec2-user você tem controle total para clonar repositórios e instalar bibliotecas sem risco de quebrar o servidor.

A presença de /usr/bin/ssm-session-worker é a prova categórica: a conexão foi estabelecida pelo Systems Manager, sem a porta 22 aberta para a internet.

1. Como Funciona o Acesso via SSH (Tradicional)
Autenticação por Par de Chaves: 
	- O usuário precisa possuir localmente o arquivo de chave privada (.pem) correspondente à chave pública instalada na EC2 (authorized_keys).
	- O usuário precisa ter uma chave SSH e precisa liberar uma regra de entrada para se conectar no servidor

2. Como Funciona o Acesso via SSM (Systems Manager)
Autenticação via IAM: 
	- O usuário não usa chaves .pem. O acesso é validado pelas políticas do AWS IAM (com suporte a MFA, SSO e Session Policies).
	- No SSM o mecanismos de comunicação é outro, ao invés de liberar regras de entrada no servidor, não precisamos liberar nada, porque a comunicação com o SSM acontece de forma inversa. Na AWS existe um Agente SSM e ele, a partir do start do usuário ele abre a comunicação com o usuário, mas isso é um serviço da AWS, para esse agente iniciar, ele precisa de autorização e no script tem essa autorização, para abrir um canal de comunicação e se conectar com a instância.
