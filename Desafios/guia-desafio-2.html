Como ler as etiquetas de cada passo

POWERSHELL = o PowerShell do Windows, como administrador · WSL = o Ubuntu dentro do seu Windows · EC2 = a máquina remota, depois do start-session · CONSOLE = o navegador, no Console da AWS.

Trocar de máquina no meio do caminho é o erro mais comum de quem segue tutorial de nuvem. O prompt à esquerda do comando é o sinal mais confiável de onde você está:

As duas camadas que todo acesso na AWS atravessa

Todo pedido feito à AWS passa por duas camadas independentes e sequenciais. A primeira é uma cancela de rede; a segunda, a conferência de um crachá.

 +--------------------------------------------------------------+
 |  1. COMUNICACAO                                              |
 |     Eu consigo chegar ate o servico?                         |
 |     VPC + Subnet + Rotas + Internet/NAT Gateway + SG         |
 +----------------------------+---------------------------------+
                              v
 +--------------------------------------------------------------+
 |  2. AUTORIZACAO                                              |
 |     Agora que cheguei, posso executar essa acao?             |
 |     IAM User + IAM Role + IAM Policy                         |
 +----------------------------+---------------------------------+
                              v
                     +----------------+
                     | ACAO EXECUTADA |
                     +----------------+
RecursoPergunta que respondeRegra mnemônicaOnde aparece
Security GroupEu consigo me comunicar com esse recurso?Quem pode falar com quem?Etapa 5
IAMEu tenho autorização para executar essa ação?Quem pode fazer o quê?Etapas 2, 3 e 6
A ordem importa — e é ela que define por onde depurar

Se o Security Group do destino não permitir a conexão, a comunicação falha antes de o IAM sequer ser consultado: não adianta ter a permissão certa. E o inverso também vale — chegar até o serviço não significa poder agir sobre ele.

Identidade para pessoa × identidade para máquina

O outro eixo do desafio: usuário para gente, role para máquina.

   SUA MAQUINA (pessoa)                RECURSO NA AWS (maquina)

   WSL / Terminal                      EC2
        |                               |  nao armazena Access Key
        v                               v
   AWS CLI                           IAM ROLE
        |  usa credenciais              |
        v                               v
   IAM USER                          IAM POLICIES
        |                               +--> permissao para SSM
        v                               +--> permissao para ECR
   AWS API                             +--> permissao para outros servicos
Por que isso muda o roteiro

Nunca se cria um "usuário com senha" para um servidor — ele veste uma role e recebe credenciais rotacionadas pelo próprio serviço. É por isso que a Etapa 2 cria um user (para você) e a Etapa 6 cria uma role (para a EC2).

Este laboratório custa dinheiro se você esquecê-lo ligado

EC2 e armazenamento de imagens no ECR são cobrados fora do Free Tier. O Session Manager não tem custo adicional.

Não pule a Etapa 12. Ela destrói tudo o que foi criado. Uma EC2 esquecida de pé continua sendo cobrada todo mês.

ETAPA 0

Preparar o Windows: WSL 2 e Docker Desktop

Todo o resto do desafio acontece dentro de um Linux. O WSL 2 é o que coloca esse Linux dentro do seu Windows, e o Docker Desktop é quem vai construir as imagens. ~20 min, incluindo um reinício.

Complemento didático

Esta etapa não fazia parte do registro original do desafio. Ela foi acrescentada porque, sem ela, quem parte de um Windows limpo não tem onde executar a Etapa 1.

0.1

Instalar o WSL 2 com Ubuntu

POWERSHELL

Um comando só instala o subsistema, o kernel e a distribuição. Abra o PowerShell como administrador — sem isso a instalação para no meio.

Comando
PS> wsl --install -d Ubuntu-24.04

Reinicie o computador quando for pedido. No primeiro boot o Ubuntu pede um nome de usuário e uma senha — esses dados são só do Linux, não têm nenhuma relação com a AWS.

Conferir, de volta no PowerShell
PS> wsl -l -v
Resposta esperada
  NAME            STATE           VERSION
* Ubuntu-24.04    Running         2
A coluna VERSION precisa ser 2

Se vier 1, converta com wsl --set-version Ubuntu-24.04 2. A versão 1 não roda o Docker Desktop com a mesma integração.

Checklist
0.2

Instalar o Docker Desktop e ligar a integração com o WSL

WINDOWS

É este passo que faz o comando docker existir dentro do Ubuntu. Sem ele, a Etapa 11 não consegue construir imagem nenhuma.

Baixe o Docker Desktop e instale. Depois, dentro do aplicativo:

Caminho nas configurações

  [x] Enable integration with my default WSL distro

Uma engine só, e é por isso que o WSL 2 pesa menos

O Docker Desktop mantém uma única engine compartilhada entre Windows e Linux. Numa VM tradicional você teria dois sistemas operacionais e duas engines disputando a mesma memória.

WSL

ETAPA 3

Autenticar o terminal na AWS

É aqui que a máquina local ganha o crachá para agir em nome do usuário IAM da etapa anterior — com credenciais que expiram em 12 horas, não com uma chave eterna em disco. ~5 min.

3.1

Fazer login

WSL

O comando abre o navegador (ou imprime a URL para você abrir manualmente) e, depois da escolha da conta, grava o token temporário no profile.

Comando
$ aws login --profile formacao_aws
Ele pergunta a região
AWS Region [us-east-1]: us-east-1
Resposta esperada ao final
Updated profile formacao_aws to use arn:aws:iam::111122223333:user/formacao_aws credentials.
Use "--profile formacao_aws" to use the new credentials.
Apareceu gio: Operation not supported?

É o WSL não conseguindo abrir o navegador do Windows. Não é fatal: o próprio comando imprime a URL de autorização — copie e cole no navegador do Windows. O fluxo continua e o profile é atualizado ao final.

Checklist
3.2

Definir o contexto do shell

WSL

Este passo evita o erro mais chato do desafio inteiro. Faça agora, não depois.

Comando
$ export AWS_PROFILE=formacao_aws
$ export AWS_DEFAULT_REGION=us-east-1
Por que isso não é opcional

Os scripts do projeto BIA (Etapas 6, 7 e 8) chamam aws ec2 ... sem a flag --profile. Sem essas duas variáveis exportadas eles caem no profile default — que está vazio — e reportam que a VPC, a subnet e o Security Group "não existem", mesmo com tudo criado corretamente.

O AWS CLI não tem "contexto implícito": quando um script não passa --profile, quem define o contexto é a variável de ambiente.

Para não repetir a cada terminal novo

Acrescente as duas linhas ao fim do seu ~/.bashrc. Todo shell novo já nasce no contexto certo.

Checklist

Checklist
Por que aws login e não aws configure

Access Keys são credenciais de longa duração: quem as obtém acessa a conta indefinidamente. No fim de 2025 a AWS liberou um mecanismo mais seguro, e foi para ele que este laboratório migrou.

Access Keys (aws configure)aws login
DuraçãoIndefinida, até serem revogadas12 horas
RotaçãoManualAutomática, a cada 15 minutos
Armazenamento localChave permanente em discoToken temporário
Risco em caso de vazamentoAlto e persistenteLimitado à janela de validade
Se a sua conta ainda não tiver o aws login disponível

O caminho antigo continua funcionando. Crie uma Access Key no Console e rode:

Comando
$ aws configure --profile formacao_aws
O que ele pergunta
AWS Access Key ID     [None]: <sua-access-key>
AWS Secret Access Key [None]: <sua-secret-key>
Default region name   [None]: us-east-1
Default output format [None]: table
Chave em disco é dívida de segurança

Ela não expira sozinha. Se usar este caminho, revogue a Access Key no Console assim que terminar o laboratório.

Encerrar a sessão a qualquer momento

aws logout --profile formacao_aws descarta as credenciais temporárias. Ele também é o último comando da Etapa 12.

Dois problemas diferentes, dois serviços diferentes

aws login resolve quem eu sou — autentica o seu terminal na conta. O SSM (Etapa 9) resolve como eu entro na máquina. Confundir os dois é o que faz muita gente procurar chave SSH onde o problema era credencial de conta.

CONSOLE

É aceitável em um laboratório, numa porta de aplicação. Em produção essa origem seria restrita a um Load Balancer ou a uma faixa de IPs conhecida.

ETAPA 6

Criar a role role-acesso-ssm

O Security Group resolveu a comunicação; a role resolve a autorização da instância para conversar com os outros serviços. Sem ela a EC2 não fala com o SSM nem com o ECR — e você não entra na máquina. ~10 min, a maior parte resolvendo um AccessDenied.

Esta etapa foi desenhada para falhar na primeira execução

Não é um defeito do roteiro. O passo 6.1 vai dar AccessDenied, e é vendo a mensagem real que fica claro o que o passo 6.2 conserta. Se você já anexou a policy antes, o 6.1 passa direto — siga para o 6.3.

6.1

Rodar o script e ler o erro

WSL

Lembre do mapa: usuário para pessoa, role para máquina. A EC2 não guarda Access Key em disco — ela veste esta role.

Comando
$ ./scripts/criar_role_ssm.sh
Resposta esperada agora — o erro é o resultado
An error occurred (AccessDenied) when calling the CreateRole operation:
User: arn:aws:iam::111122223333:user/formacao_aws is not authorized to perform:
iam:CreateRole on resource: arn:aws:iam::111122223333:role/role-acesso-ssm
because no identity-based policy allows the iam:CreateRole action

Os mesmos erros se repetem para CreateInstanceProfile, AddRoleToInstanceProfile e AttachRolePolicy.

Por que isso acontece

Na Etapa 2 o usuário ganhou permissão de usar SSM e ECR, mas nenhuma de criar identidades IAM. Permissão de usar não é o mesmo que permissão de criar — e ter AmazonSSMFullAccess não dá o direito de criar a role que o SSM vai usar.

Este é exatamente o item do desafio: "configurar permissões IAM para o usuário ao invés da role".

Checklist
6.2

Anexar a inline policy ao usuário

CONSOLE

As sete ações abaixo são exatamente as que o script precisa: criar a role, criar o instance profile, ligar um ao outro, anexar a policy gerenciada e — o mais esquecido — iam:PassRole, sem o qual a Etapa 8 não consegue entregar a role à instância.

Caminho no Console
IAM -> Users -> seu usuario -> Add permissions
    -> Create inline policy -> aba JSON
Colar no editor JSON
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "iam:CreateRole",
                "iam:GetRole",
                "iam:CreateInstanceProfile",
                "iam:GetInstanceProfile",
                "iam:AddRoleToInstanceProfile",
                "iam:AttachRolePolicy",
                "iam:PassRole"
            ],
            "Resource": "*"
        }
    ]
}
Ressalva consciente sobre o "Resource": "*"

Aceitável em um laboratório descartável, não em produção. O correto seria restringir o Resource aos ARNs específicos da role e do instance profile, e condicionar o iam:PassRole ao serviço ec2.amazonaws.com.

9.2

Trocar para o usuário de trabalho

Por que não trabalhar onde você caiu

/usr/bin é reservado aos executáveis do sistema operacional e ao gerenciador de pacotes: misturar código de aplicação ali gera conflito — uma atualização do SO pode sobrescrever arquivos.

Escrever nessas pastas exige root, e rodar aplicação como root é uma falha grave de segurança.

ec2-user é o usuário padrão do Amazon Linux. Em /home/ec2-user você tem controle total para clonar repositórios e instalar bibliotecas sem risco de quebrar o servidor.
