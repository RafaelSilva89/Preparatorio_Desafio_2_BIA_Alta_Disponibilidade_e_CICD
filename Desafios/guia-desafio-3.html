Só o BIA_DIR vira variável — e o motivo

O BIA_DIR é a cópia da BIA no disco do Linux, onde o npm install e o build acontecem. Ele precisa ser variável porque os scripts do desafio o leem em tempo de execução.

A pasta do repositório — onde os três scripts vão morar e que vai para o GitHub — não vira variável: na Fase 5 você entra nela com um cd e trabalha ali dentro. Assim o guia não carrega o caminho de ninguém, e funciona igual para quem clonar em outro lugar.

São dois lugares diferentes de propósito: node_modules tem dezenas de milhares de arquivos. Se a pasta do repositório estiver no disco do Windows — mais ainda se for uma pasta sincronizada na nuvem —, isso vira sincronização sem fim e um build bem mais lento, porque o WSL acessa o disco do Windows por uma camada de tradução.

Sempre que abrir um terminal novo

Rode source ~/DESAFIOS-FUNDAMENTAIS/variaveis.sh antes de qualquer comando das próximas fases.

Já tinha um variaveis.sh de antes?

Rode o cat > deste passo mesmo assim: ele reescreve o arquivo com o conteúdo atual, incluindo o BIA_DIR, que não existia nas primeiras versões deste guia. Versões antigas também traziam um REPO_DIR com caminho absoluto e um PROJETO que não era usado por nada — reescrever o arquivo se livra dos dois.

2.2

Liberar as permissões — uma visita só ao Console

CONSOLE

Três policies resolvem tudo o que falta no desafio inteiro. Entre no Console com o usuário administrador (ou o root): o próprio usuario-xxxx não pode alterar as próprias permissões, porque iam:* está negado para ele.

Parte 1 — duas policies gerenciadas
IAM  >  Users  >  usuario-xxxx  >  Add permissions  >  Attach policies directly

    [x] AmazonRDSReadOnlyAccess    (ver o endpoint do banco, na Fase 3)
    [x] AmazonECS_FullAccess       (ver o servico e a task definition do Dia 2)

  >  Next  >  Add permissions
Procurou por AmazonECS_ReadOnlyAccess e não achou?

Essa policy gerenciada não existe. Para ECS a AWS oferece a AmazonECS_FullAccess. Como o guia só faz leitura no ECS, a alternativa de menor privilégio é uma inline com ecs:Describe* e ecs:List*; a FullAccess resolve e pode ser removida no fim do laboratório.

Sem a parte 2, o comando do passo 2.3 responde UnauthorizedOperation: o usuário tem leitura de EC2, mas não as ações que mexem no estado da instância.

Parte 2 — uma policy inline, na mesma tela
IAM  >  Users  >  usuario-xxxx  >  Add permissions  >  Create inline policy  >  JSON

   nome da policy:  PermissaoSSMInstanceProfile
Cole este JSON

Por que o iam:PassRole precisa estar aí

Associar um instance profile é entregar uma role a uma máquina. A AWS trata isso como permissão à parte, para ninguém dar a si mesmo um privilégio maior através de uma EC2. Por isso anexar AmazonEC2FullAccess sozinho não resolveria: ele não inclui PassRole.

Validar as três de uma vez, no terminal

$ aws ecs describe-services --cluster cluster-bia --services service-bia --query 'services[0].status' --output text
$ aws ec2 reboot-instances --instance-ids "$DEV_INSTANCE_ID" --dry-run
Resposta esperada
bia
ACTIVE

aws: [ERROR]: An error occurred (DryRunOperation) when calling the RebootInstances
operation: Request would have succeeded, but DryRun flag is set.

O --dry-run testa a permissão sem executar nada: DryRunOperation quer dizer "você pode". Se vier UnauthorizedOperation, a policy inline não foi salva.

A palavra ERROR aí é o sucesso

Leia a frase ao pé da letra: "a requisição teria dado certo, mas a flag DryRun está ligada". A instância não foi reiniciada.

A API do EC2 nunca devolve "sucesso" num dry-run — ela sempre levanta uma exceção, e o nome dela é a resposta: DryRunOperation significa que você tem a permissão, UnauthorizedOperation significa que falta. Como o CLI trata qualquer exceção da API como erro, ele carimba aws: [ERROR] nos dois casos. O que importa é o nome entre parênteses.

2.4

Esperar o agente se registrar

WSL

O agente subiu com a máquina, quando ainda não havia credencial nenhuma, e desde então tenta de novo em intervalos cada vez maiores. Ele se registra sozinho depois da associação — só não é imediato: costuma levar de 5 a 20 minutos.

Comando
$ for i in $(seq 1 30); do
    ping=$(aws ssm describe-instance-information \
      --filters "Key=InstanceIds,Values=$DEV_INSTANCE_ID" \
      --query 'InstanceInformationList[0].PingStatus' --output text)
    echo "tentativa $i: $ping"
    [ "$ping" = "Online" ] && break
    sleep 30
  done
Resposta esperada
tentativa 1: None
tentativa 2: None
...
tentativa 9: Online

Enquanto der None, nada está errado: o agente ainda não chegou na próxima tentativa dele. O laço acima cobre cerca de 15 minutos.

Com pressa? O reboot resolve em ~1 minuto

Reiniciar força o agente a começar do zero, já com a role no lugar. Precisa da policy do passo 2.2.

Atalho opcional
$ aws ec2 reboot-instances --instance-ids "$DEV_INSTANCE_ID"
$ sleep 60
$ aws ssm describe-instance-information \
  --filters "Key=InstanceIds,Values=$DEV_INSTANCE_ID" \
  --query 'InstanceInformationList[0].PingStatus' --output text
Resposta esperada
Online

O reboot-instances não imprime nada quando dá certo — o silêncio é sucesso.

Passou de 20 minutos e continua None?

Confira, nesta ordem: a associação ainda está associated (comando do 2.3) e a máquina está running com os checks em passed (aws ec2 describe-instance-status --instance-ids "$DEV_INSTANCE_ID"). Se os dois estiverem certos, reinicie pelo atalho acima.

9.3

Pausar o laboratório para não ser cobrado

WSL
Só depois de gravar as evidências do passo 9.2

Parar a EC2 do cluster derruba a API, e o site passa a carregar sem dados. Faça os prints e guarde as saídas antes.

São três coisas cobrando por hora neste laboratório: a bia-dev, a EC2 do cluster ECS e o RDS. Pausar as três é o suficiente para o gasto por hora parar.

1. Parar a bia-dev
$ aws ec2 stop-instances --instance-ids "$DEV_INSTANCE_ID" \
  --query 'StoppingInstances[].{Id:InstanceId,De:PreviousState.Name,Para:CurrentState.Name}' --output table
Resposta esperada
-------------------------------------------------
|                 StopInstances                 |
+-----------+----------------------+------------+
|    De     |         Id           |   Para     |
+-----------+----------------------+------------+
|  running  | i-xxxxxxxxxxxx-dev  | stopping   |
+-----------+----------------------+------------+

Essa é segura: a bia-dev é alcançada por SSM, que não depende de IP. Quando você religar, o start-instances devolve a máquina e o agente volta sozinho.

2. Derrubar a EC2 do cluster (pelo Auto Scaling)
$ ASG=$(aws autoscaling describe-auto-scaling-groups \
  --query "AutoScalingGroups[?contains(AutoScalingGroupName, 'cluster-bia')].AutoScalingGroupName" \
  --output text)
$ echo "$ASG"
$ aws autoscaling update-auto-scaling-group \
  --auto-scaling-group-name "$ASG" \
  --min-size 0 --desired-capacity 0
Resposta esperada
Infra-ECS-Cluster-cluster-bia-xxxxxxxx-ECSAutoScalingGroup-xxxxxxxxxxxx

O update-auto-scaling-group não imprime nada quando dá certo. Em um ou dois minutos a instância é encerrada.

Não adianta parar essa instância direto

Ela pertence a um Auto Scaling Group com desired = 1. Se você usar stop-instances ou terminate-instances nela, o ASG entende que faltou capacidade e sobe outra no lugar — e a cobrança continua. Quem manda é a capacidade desejada.

Para religar

O mesmo comando com --min-size 1 --desired-capacity 1. A instância nova sobe, se registra no cluster, e o serviço service-bia recoloca a task — mas com IP público novo. Volte ao passo 1.1 e refaça a Fase 6.

9.4

Parar o RDS e conferir o que sobrou

CONSOLE

O RDS é a maior parte da conta neste laboratório, e é o único item que o seu usuário não consegue parar pelo terminal: AmazonRDSReadOnlyAccess só lê.

Caminho no Console
RDS  >  Databases  >  bia  >  Actions  >  Stop temporarily
O RDS parado religa sozinho em 7 dias

É regra da AWS. Se o laboratório for ficar parado mais que isso, o certo é apagar a instância (Actions > Delete) — com snapshot, se quiser poder recriar depois.

Conferir se sobrou algo ligado
$ aws ec2 describe-instances \
  --filters "Name=instance-state-name,Values=running" \
  --query 'Reservations[].Instances[].[InstanceId,Tags[?Key==`Name`]|[0].Value]' --output text
$ aws rds describe-db-instances \
  --query 'DBInstances[].[DBInstanceIdentifier,DBInstanceStatus]' --output text
Resposta esperada
bia     stopped

Nenhuma linha de EC2 e o RDS em stopped: a cobrança por hora acabou.

O que continua custando, mesmo com tudo parado

Os discos EBS das máquinas (aqui são 4 volumes, 68 GB no total) e o armazenamento do RDS continuam sendo cobrados enquanto existirem — parar uma EC2 não apaga o disco dela. É alguns dólares por mês, não por hora. O bucket S3 com o site é desprezível: alguns MB.

Se o laboratório acabou de vez, veja o bloco abaixo.

Encerrar de vez, sem deixar nada cobrando

Ordem importa: apague a stack do cluster antes das instâncias, senão o Auto Scaling recria o que você encerrar.

Comando
$ aws ecs update-service --cluster cluster-bia --service service-bia --desired-count 0
$ aws ecs delete-service --cluster cluster-bia --service service-bia --force
$ aws ec2 terminate-instances --instance-ids "$DEV_INSTANCE_ID" i-xxxxxxxxxxxx-01 i-xxxxxxxxxxxx-02
$ aws s3 rm "s3://$BUCKET_NAME" --recursive
E no Console, o que o CLI não alcança
ECS   >  Clusters  >  cluster-bia  >  Delete cluster
         (isso apaga a stack do CloudFormation e o Auto Scaling Group)
RDS   >  Databases  >  bia         >  Actions  >  Delete
EC2   >  Volumes    >  apagar os que ficarem "available" (orfaos)
S3    >  o bucket pode ficar: vazio ele nao custa nada

Depois de tudo, confira em Billing > Bills no dia seguinte: é a única fonte que diz a verdade sobre o que ainda está gerando custo.

Trocar a senha do banco, se ela tiver circulado

A senha do RDS anda em texto puro na task definition, e no passo 4.3 ela passa pelo seu terminal. É fácil ela acabar num print, no ~/.bash_history, num log colado numa conversa de suporte ou num repositório. Se isso aconteceu, troque — leva dois minutos.

A ordem importa: se você trocar no RDS e parar por aí, a API perde a conexão e o site volta a dar 500.

1. Nova senha no banco
RDS  >  Databases  >  bia  >  Modify  >  New master password
     >  Continue  >  Apply immediately
2. Mesma senha na task definition
ECS  >  Task definitions  >  task-def-bia  >  Create new revision
     >  Container  >  Environment variables  >  DB_PWD = (a nova senha)
     >  Create
3. Fazer o serviço pegar a revisão nova
$ aws ecs update-service --cluster cluster-bia --service service-bia \
  --force-new-deployment

Confirme com curl -s -i "$API_URL/api/tarefas" depois de um ou dois minutos: tem que continuar 200. O jeito de não precisar disso é o Secrets Manager, citado no passo 3.4.
