💡 Explicação do Fluxo:

Aqui está a explicação detalhada de cada parte do comando zip -r ../bia.zip docker-compose.yml:

• zip: É o comando principal, que chama o programa responsável por compactar arquivos.

• -r: É uma "flag" (opção) que significa recursivo (recursive). Ela instrui o comando a incluir não apenas a pasta selecionada, mas também todos os arquivos e subpastas dentro dela
	- Nota: No seu caso específico, como você está compactando apenas um arquivo único (docker-compose.yml), o -r acaba não tendo efeito prático, mas é um hábito comum deixá-lo no comando caso você queira adicionar pastas no futuro.

• ../bia.zip: Este é o destino do arquivo que será criado.

	- O ../ é um atalho de navegação que significa "volte um nível de diretório" (ou seja, salve na pasta pai).
	- bia.zip é o nome que o arquivo final terá.

• docker-compose.yml: Esta é a origem, ou seja, o nome do arquivo atual (que está dentro da pasta onde o comando foi executado) que será colocado dentro do .zip.

Como o comando anterior no seu script era cd bia (entrar na pasta "bia"), este comando diz: "Pegue o arquivo docker-compose.yml que está aqui dentro da pasta bia, compacte-o, e salve o resultado com o nome bia.zip na pasta de fora (a pasta pai, desafios-fundamentais)."

Este comando faz exatamente o processo inverso do que fizemos antes, descompactando o arquivo para verificarmos se tudo ocorreu bem. Aqui está a explicação detalhada de cada parte:

• unzip: É o comando principal responsável por extrair arquivos compactados no formato .zip.

• -o: É uma opção que significa overwrite (sobrescrever). Ela diz ao sistema para substituir arquivos existentes sem perguntar "Você tem certeza?". Se a pasta ou o arquivo já estiverem lá, eles serão atualizados silenciosamente.

• bia.zip: É o arquivo de origem, ou seja, o arquivo compactado que criamos no passo anterior e que agora queremos abrir.

• -d bia2: A opção -d significa directory (diretório/pasta) de destino. Ela diz ao comando: "Não extraia os arquivos soltos aqui onde estou; coloque todos eles dentro de uma pasta chamada bia2". Se a pasta bia2 não existir, o próprio comando a cria automaticamente.

Resumo do que acontece no script:
O comando diz: "Pegue o arquivo bia.zip, descompacte o seu conteúdo e coloque tudo dentro de uma nova pasta chamada bia2, sobrescrevendo os arquivos caso já existam." Como resultado, você pode ver no seu explorador de arquivos que a pasta bia2 apareceu contendo o docker-compose.yml intacto.

🔍 Entendendo o Script e o Command Substitution
Este script demonstra um conceito poderosíssimo no shell script chamado Command Substitution (Substituição de Comando). Veja o passo a passo do que está acontecendo:

NOME=$1 (Linha 1): O script pega o primeiro argumento que você digita no terminal ao executá-lo (neste caso, a palavra bia-dev) e o guarda na variável $NOME.

$( ... ) (Linhas 2 a 5): Este é o Command Substitution. Em vez de executar o comando da AWS e jogar o resultado perdido na tela, a sintaxe $(comando) diz ao shell: "Execute tudo o que está aqui dentro, pegue a resposta final e salve na variável INSTANCE_ID".

O Comando AWS (Linhas 2 a 5): Ele usa o aws ec2 describe-instances para buscar uma máquina. Ele filtra pela tag de nome (bia-dev), garante que a máquina está ligada ('running') e usa o --query para extrair da resposta JSON apenas o ID da instância em formato de texto simples.

echo $INSTANCE_ID (Linha 8): Após a busca na AWS ter terminado e o ID ter sido guardado em silêncio, este comando imprime o valor salvo na tela.

Resumo da Execução no Terminal:
Quando você roda ./04-command_substitution.sh bia-dev, o script vai até a AWS de forma invisível, procura a EC2 chamada "bia-dev", captura o ID dela e o devolve limpo no seu terminal (i-04c0b663818ca4306). Quando você rodou com bia-dev2, provavelmente ele não retornou nada porque essa máquina não existia ou não estava rodando!

O projeto BIA está rodando na porta 3001, mas eu quero acessa a BIA da minha máquina, sem ter que liberar nenhuma porta para o mundo, a solução é criar um Túnel. Esse recurso irá rodar de forma privada, para o usuário. 

O Túnel é um mapeamento de porta.

Como funciona essa estratégia?
O que você está implementando se chama Port Forwarding (Redirecionamento de Portas) utilizando o AWS Systems Manager (SSM).

1. O Problema Inicial: Normalmente, para acessar a aplicação "bia" rodando na porta 3001 da sua EC2, você precisaria abrir essa porta no Security Group (3001: 0.0.0.0/0). O problema é que isso deixa a sua aplicação exposta para a internet inteira (qualquer pessoa pode tentar acessar).
2. O Túnel SSM: O AWS SSM permite criar um "túnel" seguro entre a sua máquina local (a VM) e a instância EC2, sem precisar abrir portas para a internet no Security Group.
3. O Redirecionamento (3002:3001): Você configura esse túnel para pegar uma porta da sua máquina local (ex: 3002) e conectá-la diretamente à porta onde a aplicação está rodando na EC2 (3001).
4. O Acesso Final: Ao invés de acessar o IP público da EC2, você abre o navegador na sua própria máquina e acessa localhost:3002. O túnel pega esse acesso, envia de forma segura para a AWS e o entrega na porta 3001 da EC2. Para a EC2, parece que o acesso veio de dentro dela mesma.

Vantagens:
	- Segurança Elevada: É a maior vantagem. Você não precisa expor a porta da sua aplicação (3001) para a internet 0.0.0.0/0. Apenas quem tem acesso à sua conta AWS e permissões do SSM consegue criar esse túnel.
	- Redução da Superfície de Ataque: Como a porta não está aberta no Security Group para a web, hackers e bots que escaneiam a internet não conseguirão sequer ver que a sua aplicação existe.
	- Acesso Simplificado: Você não precisa se preocupar em gerenciar chaves SSH complexas, o SSM gerencia a autenticação através das suas credenciais (IAM) da AWS.

O código:

NOME=$1
INSTANCE_ID=$(aws ec2 describe-instances \
               --filter "Name=tag:Name,Values=$NOME" \
               --query "Reservations[].Instances[?State.Name == 'running'].InstanceId[]" \
               --output text --profile desafios-fundamentais)

#check if my instance_id is empty
if [ -z "$INSTANCE_ID" ]; then
    echo "Instancia nao encontrada"
    exit 1
fi
echo "Instancia encontrada: $INSTANCE_ID"

#create the port forwarding tunnel
aws ssm start-session --target $INSTANCE_ID \
                       --document-name AWS-StartPortForwardingSession \
                       --parameters '{"portNumber":["3001"],"localPortNumber":["3002"]}' --profile desafios-fundamentais

🔍 Como funciona essa nova arquitetura (SSM + RDS)?

Agora você não tem apenas um túnel, mas dois redirecionamentos passando pela conexão segura do AWS Systems Manager (SSM). A sua EC2 (bia-dev) está atuando como um "Bastion Host" (ou máquina de salto) para conectar sua máquina local aos recursos privados da AWS.

• Túnel da Aplicação (3002:3001): Como vimos antes, sua máquina local na porta 3002 se conecta à porta 3001 da EC2, permitindo que você acesse a aplicação web pelo seu navegador sem abrir a porta no Security Group para a internet.

• Túnel do Banco de Dados (5433:5432): Aqui está a novidade! Você está mapeando a porta local 5433 da sua máquina para se conectar à porta 5432 do RDS (via EC2).
	- Por que 5433? É comum utilizarmos a 5433 na nossa máquina local porque a porta padrão do PostgreSQL (5432) já pode estar sendo usada por um banco instalado diretamente no seu computador.

• Comunicação EC2 ➔ RDS: A sua aplicação rodando na EC2 continua se conectando normalmente ao banco de dados RDS através do endpoint gerado pela AWS, usando a rede interna rápida e segura da própria infraestrutura.

💡 Vantagens dessa Estratégia

1. Segurança Extrema para o Banco: O seu RDS não precisa ser público. Ele pode residir em uma sub-rede privada, invisível para a internet. A única forma de acessá-lo externamente é através desse túnel autenticado via SSM.

2. Facilidade de Gestão Local: Com o túnel ativo, você pode abrir ferramentas de banco de dados na sua própria máquina (como o DBeaver, pgAdmin ou TablePlus), apontar para localhost:5433 e gerenciar o RDS que está lá na AWS como se ele estivesse rodando no seu próprio computador.

3. Zero Portas Expostas: Assim como a regra do 0.0.0.0/0 na porta 3001 deixa de ser necessária, você também não precisa liberar o seu IP residencial (que costuma ser dinâmico e mudar com frequência) no Security Group do banco de dados.

Tudo flui através do SSM de forma criptografada!
