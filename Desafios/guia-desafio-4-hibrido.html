Montar o porteiro pelo Console, provar que funciona pelo terminal

O mesmo desafio do porteiro e dos túneis SSM, agora dividido em dois papéis. O Console da AWS cria cada peça — VPC, security groups, banco, role e máquinas — com cada campo explicado. O terminal e o DBeaver entram só para conectar e testar. Tudo é um laboratório novo, com nomes lab-*: nada do ambiente da BIA é tocado, e no fim você apaga tudo pelo Console.

Como ler as etiquetas de cada passo

CONSOLE = navegador, logado no Console da AWS · WSL = terminal Ubuntu · WSL · T1 / T2 / T3 = primeira, segunda e terceira aba do terminal (um túnel prende a aba onde roda) · DBEAVER = o cliente de banco no Windows · NAVEGADOR = navegador acessando localhost.

Este laboratório cobra por hora enquanto estiver ligado

Valores aproximados em us-east-1, sem free tier: cada EC2 t3.micro ≈ US$ 0,0104/h, cada IPv4 público ≈ US$ 0,005/h, o RDS db.t3.micro ≈ US$ 0,018/h mais o disco. Somando tudo, algo perto de US$ 0,06 por hora. O NAT Gateway, que custaria bem mais, fica de fora de propósito. Confira no AWS Pricing Calculator e faça a Fase 10 no mesmo dia.

cat > ~/DESAFIOS-FUNDAMENTAIS/lab-hibrido.shTudo o que o cat receber vai para esse arquivo. O > cria o arquivo — ou apaga e reescreve, se ele já existir

Rode este bloco uma vez só, no começo

Por causa do >, rodar de novo depois das outras fases apaga os nomes já anotados e deixa só as três primeiras linhas. Se isso acontecer, refaça os blocos "Anotar o nome" das fases que você já passou.

O arquivo começa só com o profile e a região. Os nomes dos recursos entram um a um, na fase em que cada recurso é criado — procure os blocos "Anotar o nome". Assim você vê onde cada variável nasce e onde ela é usada.

Por que um arquivo, e não só export

Uma variável criada com export vive só na aba onde foi digitada. Nas Fases 7 e 8 você abre abas novas para os túneis, e elas começam vazias. O arquivo é o caderno dessas abas: um source e todos os nomes anotados até ali voltam. Ele guarda só nomes — nunca IDs, IPs ou senha.

A VPC custa alguma coisa?

Não por existir. A VPC e tudo o que este assistente criou — subnets, tabelas de rota, Internet Gateway, security groups e network ACLs — não têm cobrança própria. O que cobra numa VPC são estes itens:

  • NAT Gateway — por hora e por GB. Evitado: você marcou None.
  • VPC endpoint do tipo interface — por hora. Evitado: None.
  • Flow Logs — pelo volume de log gravado. Não foi ligado.
  • IPv4 público — cerca de US$ 0,005 por hora, por IP. Entra na Fase 5, com o IP público das EC2.
  • Tráfego de dados — saída para a internet e tráfego entre zonas diferentes. No laboratório são poucos megabytes.

Com a Fase 1 pronta, essa VPC ainda não está cobrando nada. O relógio começa no RDS (Fase 3) e nas EC2 (Fases 5 e 6) — e para de vez na Fase 10.

Compare as respostas dos itens D e E. Não existe um campo "tipo de subnet": a única diferença entre as duas é a linha 0.0.0.0/0 → igw-....

Quem não tem essa rota não sai nem entra da internet, mesmo tendo IP público.

As subnets públicas deste assistente não dão IP público sozinhas

A opção Auto-assign public IPv4 vem desligada nelas. Por isso, na Fase 5 você vai ligar Auto-assign public IP na hora de lançar cada EC2. Sem IP público, a máquina não chega ao serviço do SSM e nunca aparece como Online — foi o problema da aula de conectividade pública.

#!/bin/bash
# lab-app: API minima que le a tabela "tarefas" do RDS.
# O user data roda uma vez, como root, no primeiro boot da instancia.
# A senha do banco NAO fica aqui: ela entra depois em /etc/lab-app.env.

dnf install -y python3-psycopg2

mkdir -p /opt/lab-app
cat > /opt/lab-app/app.py <<'APP'
import json
import os
from http.server import BaseHTTPRequestHandler, HTTPServer

import psycopg2

VERSAO = "lab-app 1.0"


def conectar():
    return psycopg2.connect(
        host=os.environ["DB_HOST"],
        port=os.environ.get("DB_PORT", "5432"),
        dbname=os.environ.get("DB_NAME", "lab"),
        user=os.environ.get("DB_USER", "postgres"),
        password=os.environ["DB_PWD"],
        sslmode="require",
        connect_timeout=5,
    )


def listar_tarefas():
    conn = conectar()
    try:
        with conn.cursor() as cur:
            cur.execute(
                "SELECT uuid, titulo, importante, created_at "
                "FROM tarefas ORDER BY created_at"
            )
            colunas = [c[0] for c in cur.description]
            return [dict(zip(colunas, linha)) for linha in cur.fetchall()]
    finally:
        conn.close()


class Handler(BaseHTTPRequestHandler):
    def responder(self, status, corpo):
        dados = json.dumps(corpo, default=str, ensure_ascii=False).encode("utf-8")
        self.send_response(status)
        self.send_header("Content-Type", "application/json; charset=utf-8")
        self.send_header("Content-Length", str(len(dados)))
        self.end_headers()
        self.wfile.write(dados)

    def do_GET(self):
        if self.path == "/api/versao":
            self.responder(200, {"versao": VERSAO})
        elif self.path == "/api/tarefas":
            try:
                self.responder(200, listar_tarefas())
            except KeyError as erro:
                self.responder(500, {"erro": f"variavel {erro} ausente em /etc/lab-app.env"})
            except psycopg2.Error as erro:
                self.responder(500, {"erro": str(erro).strip()})
        else:
            self.responder(404, {"erro": "rota nao encontrada"})


if __name__ == "__main__":
    HTTPServer(("0.0.0.0", 80), Handler).serve_forever()
APP

cat > /etc/systemd/system/lab-app.service <<'UNIT'
[Unit]

[Service]

[Install]

Por que a senha não está no user data

Qualquer pessoa com permissão de ver a instância lê o user data no Console (Actions › Instance settings › Edit user data), em texto puro. Senha ali é senha exposta. Por isso o user data instala e deixa a app pronta, e a senha entra no próximo passo, por uma sessão SSM.
