Conectar sua VM à sua conta na AWS (usuário IAM)

Existem dois recursos básicos que precisa ter o conhecimento:

1. Security Group para comunicação
2. IAM para autorização

Você pode explicar esse conceito como uma sequência de duas camadas fundamentais: Comunicação e Autorização.

A ideia principal é:

Primeiro, eu preciso conseguir chegar ao serviço. Depois, preciso ter permissão para executar uma ação nele.

1. Security Group: permite a comunicação

O primeiro requisito é a conectividade de rede.

Imagine que eu tenho uma aplicação rodando em uma instância EC2 e essa aplicação precisa acessar outro recurso da AWS, como um banco de dados RDS.

Antes de pensar em permissões, precisamos responder:

A minha aplicação consegue se comunicar com esse recurso pela rede?

É nesse ponto que entram elementos como:

- VPC
- Subnet
- Rotas
- Internet Gateway ou NAT Gateway, quando necessário
- Security Groups

O Security Group funciona como uma camada de controle de tráfego.

Ele define, por exemplo:

- quem pode chegar até o recurso
- por qual protocolo
- em qual porta
- de onde vem a comunicação

Exemplo

+------------------+                 +------------------+
|                  |                 |                  |
|       EC2        |  ---- 3306 ---> |       RDS        |
|   Aplicação      |                 |    MySQL         |
|                  |                 |                  |
+------------------+                 +------------------+
        │              			          │
        │               		          │
        └───── Security Group ───────┘
              Permite comunicação?

Se o Security Group do RDS não permitir conexões da EC2 na porta 3306, a aplicação nem consegue estabelecer a conexão com o banco.

Nesse caso, não adianta a aplicação ter usuário, senha ou permissões no banco.

A comunicação falha antes.


2. IAM: permite a autorização

Agora vamos imaginar que a comunicação de rede está funcionando.

A aplicação consegue chegar até o serviço.

Porém, surge uma nova pergunta:

Mesmo conseguindo chegar até o serviço, eu tenho autorização para executar a ação que quero?

É nesse momento que entra o IAM — Identity and Access Management.

O IAM controla quem pode fazer o quê em qual recurso.

Por exemplo:

Identidade:
EC2 / Usuário / Role
        │
        ▼
+-------------------------+
|           IAM           |
|                         |
| Pode acessar o S3?      |
| Pode listar arquivos?   |
| Pode criar arquivos?    |
| Pode deletar arquivos?  |
+-------------------------+
        │
        ▼
     Permitido?

Uma policy poderia determinar:

EC2
 │
 │ Quero executar:
 │ s3:GetObject
 ▼
+--------------------+
|       IAM Role     |
|                    |
| s3:GetObject  ✓    |
| s3:DeleteObject ✗  |
+--------------------+

Nesse caso, a aplicação consegue acessar um arquivo no S3, mas não consegue deletá-lo.

A diferença entre os dois

Podemos resumir assim:

| Recurso            | Pergunta que responde                             |
| ------------------ | ------------------------------------------------- |
| **Security Group** | Eu consigo **me comunicar** com esse recurso?     |
| **IAM**            | Eu tenho **autorização** para executar essa ação? |

Ou, de uma forma ainda mais simples:

┌───────────────────────────────────────────────┐
│                     1. COMUNICAÇÃO                              │
│                                                                 │
│  "Eu consigo chegar até o serviço?"                             │
│                                                                 │
│  VPC + Subnet + Rotas + Security Group                          │
└──────────────────────┬────────────────────────┘
                                │
                                ▼
┌───────────────────────────────────────────────┐

│                                                                 │
│  "Agora que cheguei, tenho permissão para fazer essa ação?"     │

                      ┌─────────────┐

Permissões IAM (Autorização)

• Para que serve
• Usuário vs Role
• Criando nosso primeiro usuário
• Configurando Credenciais
• Concedendo nossa primeira permissão

A diferença principal é o que cada recurso controla:

• Security Group → controla a comunicação de rede
• IAM → controla permissões e acesso aos recursos da AWS
• Ele controla o tráfego de entrada (Inbound) e saída (Outbound).

Você pode dizer:

"Quero permitir que a Internet acesse minha EC2 pela porta 80."

Isso é Security Group.

Uma forma simples de memorizar:

• Security Group = "Quem pode falar com quem?"
• IAM = "Quem pode fazer o quê?"
• IAM (Identity and Access Management) controla identidades e permissões dentro da AWS.

Por exemplo:

"O usuário Rafael pode acessar o S3, mas não pode excluir uma EC2."

Isso é IAM.

A diferença na prática

====================================================================================================

--- ACESSO E GERENCIAMENTO ---
TERMINAL / USER IAM KEYS : Computador local do desenvolvedor ou pipeline automatizado acessando a AWS via linha de comando com chaves de acesso.
AWS CONSOLE              : Interface web da AWS para gerenciamento visual da infraestrutura.

--- REDE E SEGURANÇA ---
VPC (Virtual Private Cloud): Rede virtual isolada na AWS que protege todos os recursos da aplicação.
SUBNET                     : Sub-rede dentro da VPC onde o servidor EC2 está alocado.
IPV4 PÚBLICO               : Representa a tentativa de acesso via internet. A marca "X" indica bloqueio ou controle rigoroso (fechado para o mundo).
SG (Security Group)        : O firewall virtual exclusivo do servidor EC2. Ele define quais portas podem receber tráfego (ex: libera apenas a porta 3001).

--- COMPUTAÇÃO E APLICAÇÃO ---
BIA-DEV (EC2)            : Máquina virtual (servidor) de desenvolvimento (BIA-DEV) rodando na AWS.
Porta 3001               : Porta exposta no EC2 para receber as requisições direcionadas à aplicação.
CONTAINER [3001:8080]    : Contêiner Docker rodando no EC2. O tráfego que chega na porta 3001 do EC2 é redirecionado para a porta 8080 dentro do contêiner.
AGENTE IA                : O código/aplicação real (Inteligência Artificial) executando isolado dentro do contêiner.

--- PERMISSÕES (IAM) ---
ROLE                     : Identidade (perfil de acesso) assumida pelo EC2. Permite que o servidor acesse outros serviços da AWS sem precisar de senhas fixas no código.
POLICY                   : Conjunto de regras de permissão anexadas à Role:
  - SSMFullAccess        : Permite acesso remoto seguro ao EC2 via AWS Systems Manager.
  - ECRFullAccess        : Permite que o EC2 faça o download (pull) das imagens Docker do repositório.

--- SERVIÇOS AWS COMPLEMENTARES ---
SSM (Systems Manager)    : Serviço que permite acessar o terminal do EC2 de forma segura pelo painel da AWS, dispensando o uso de SSH (porta 22).
ECR (Elastic Cont. Reg.) : Repositório privado de imagens Docker. É de onde o EC2 baixa a imagem do "Agente IA" para rodar o contêiner.
ECS, S3, EB              : Outros serviços da AWS (Elastic Container Service, Simple Storage Service, Elastic Beanstalk) disponíveis no ambiente/ecossistema.

Por que evitar o /usr e /usr/bin?
Pastas de Sistema: O diretório /usr/bin é reservado para os executáveis básicos do sistema operacional e para os programas oficiais instalados pelo gerenciador de pacotes da AWS.

Risco de Conflitos: Colocar o código da sua aplicação ali mistura os seus arquivos com os do sistema. Se o sistema operacional atualizar, seus arquivos podem ser sobrescritos ou causar erros.

Segurança: Para escrever e rodar coisas nessas pastas do sistema, você frequentemente precisará de privilégios de root (administrador máximo), e rodar aplicações como root é uma falha grave de segurança.


Por que o ec2-user é a escolha certa?
Usuário Padrão: O ec2-user é o usuário oficial e padrão criado pela AWS para o Amazon Linux.

Ambiente Isolado: Ao rodar sudo su - ec2-user, você vai automaticamente para a pasta /home/ec2-user. É o seu "espaço de trabalho" seguro dentro da EC2.

Permissões Corretas: Dentro do /home/ec2-user, você tem controle total para criar pastas, baixar repositórios do Git e instalar bibliotecas sem correr o risco de quebrar o servidor.

Para acessar ec2-user:
	- sudo su - ec2-user

Fazer conexão da sua VM para bia-dev tanto por ssh quanto por ssm


Aqui estão os requisitos exatos para configurar essa conexão via SSM:


1. Na sua Máquina Local (Seu Computador)
Para o seu terminal conseguir iniciar a comunicação e abrir o túnel interativo, você precisa de dois componentes instalados:

AWS CLI (Command Line Interface): Precisa estar instalado e configurado (usando o comando aws configure). Você deve fornecer credenciais (Access Key e Secret Key) de um usuário IAM que tenha permissão para executar a ação ssm:StartSession.

Session Manager Plugin: Este é o grande "segredo"! O AWS CLI sozinho não consegue abrir a tela interativa do terminal. Você precisa baixar e instalar esse plugin oficial da AWS no seu sistema operacional. Quando você roda o comando, o AWS CLI aciona esse plugin em segundo plano.

2. Na AWS (Sua Instância EC2)
A máquina que vai receber a conexão também precisa estar pronta. Felizmente, grande parte disso já vem pré-configurada em sistemas modernos:

Agent do SSM Instalado: O software amazon-ssm-agent deve estar rodando na máquina. Como você escolheu o Amazon Linux 2023, ele já vem instalado e ativo por padrão.

Permissão IAM (Role): A sua EC2 precisa de autorização para conversar com o serviço Systems Manager. É necessário anexar uma Função IAM à instância (geralmente contendo a política AmazonSSMManagedInstanceCore). Inclusive, no print que você mandou lá no início, dá para ver exatamente isso: a sua EC2 possui a role role-acesso-ssm anexada!

Acesso à Rede: A instância precisa conseguir alcançar os servidores da AWS. Isso significa que ela deve ter saída para a internet (via Sub-rede Pública ou NAT Gateway) ou usar VPC Endpoints (se for um ambiente privado restrito).

Se alguma dessas 5 pontas estiver faltando, o terminal simplesmente exibe um erro de timeout ou diz que a instância não está online.

Essas configurações foram realizadas na etapa:
• Finalizar preparação da sua máquina de trabalho com o que foi passado hoje
• Conectar sua VM à sua conta na AWS (usuário IAM)

Para que a conexão via SSM funcione perfeitamente, precisamos de um agente e de autorizações muito bem definidas no IAM da AWS. Essa comunicação depende de dois grandes blocos de permissões: a autorização da máquina e a sua autorização.

O Agente: Existe um programa chamado SSM Agent que fica instalado dentro da nossa instância EC2. Ele é o responsável por manter a comunicação da máquina com o serviço central do AWS Systems Manager.

A Autorização da Máquina (Role): A nossa EC2 precisa de permissão para conversar com a AWS. Nós nunca criamos um "usuário" com senha para uma máquina. Em vez disso, nós criamos uma Role (Função IAM) e a "vestimos" na EC2.

As Permissões (Policies): As autorizações dentro da AWS acontecem através de Policies (Políticas). Cada policy concede um poder específico. Para a EC2 usar o SSM, nós associamos à Role dela a policy chamada AmazonSSMManagedInstanceCore. (Outros exemplos de policies usadas na AWS são: AmazonEC2ContainerRegistryPowerUser, AmazonRDSFullAccess, etc.)

1. Como Funciona o Acesso via SSH (Tradicional)
Autenticação por Par de Chaves: 
	- O usuário precisa possuir localmente o arquivo de chave privada (.pem) correspondente à chave pública instalada na EC2 (authorized_keys).
	- O usuário precisa ter uma chave SSH e precisa liberar uma regra de entrada para se conectar no servidor

2. Como Funciona o Acesso via SSM (Systems Manager)
Autenticação via IAM: 
	- O usuário não usa chaves .pem. O acesso é validado pelas políticas do AWS IAM (com suporte a MFA, SSO e Session Policies).
	- No SSM o mecanismos de comunicação é outro, ao invés de liberar regras de entrada no servidor, não precisamos liberar nada, porque a comunicação com o SSM acontece de forma inversa. Na AWS existe um Agente SSM e ele, a partir do start do usuário ele abre a comunicação com o usuário, mas isso é um serviço da AWS, para esse agente iniciar, ele precisa de autorização e no script tem essa autorização, para abrir um canal de comunicação e se conectar com a instância.

Fazendo conexão por aws login

Só que no final de 2025, a AWS liberou um mecanismo mais seguro para a gente realizar esse trabalho, que é utilizando a AWS Login.
Na aula anterior foi criado o usuário e configuramos apenas acesso com Security Credentials. Nós não vamos mais trabalhar dessa forma,trabalhando com Security Credentials. A gente vai trabalhar com credenciais temporárias, aquelas Security Credentials são credenciais de longa duração. Obviamente, se alguém pega essas credenciais, elas podem acessar a sua conta. 1. aws login (A sua Identidade / O Crachá)
O aws login resolve o problema de Autenticação. Ele serve para provar para a AWS quem você é e liberar o seu terminal (WSL) para executar comandos na sua conta.

O que ele substitui: Substitui as antigas "Access Keys" e "Secret Keys" (Security Credentials) que ficavam salvas no seu computador para sempre e eram um risco de segurança.

Como funciona: Como você mesmo explicou perfeitamente, ele gera credenciais temporárias (duram 12h, rotacionam a cada 15 min). É como se você fosse na recepção do prédio e pegasse um crachá de visitante que só vale por aquele dia.

Resumo: Ele não conecta na máquina virtual (EC2). Ele apenas diz: "AWS, meu terminal WSL agora tem permissão temporária para agir em nome do usuário formacao_aws".

2. SSM - Systems Manager (A Porta de Entrada / O Túnel)
O SSM resolve o problema de Conexão com a Máquina. Ele é o serviço da AWS que permite que você abra um terminal dentro da sua instância EC2.

O que ele substitui: Substitui o famoso SSH, onde você precisava de um arquivo de chave .pem e precisava deixar a porta 22 da máquina aberta para a internet (o que é menos seguro).

Como funciona: Ele cria um túnel seguro diretamente pela rede interna da AWS usando o seu CLI. É como se fosse a chave que abre especificamente a porta da sala (sua máquina EC2) dentro do prédio.

Resumo: É o comando que de fato vai fazer a sua tela preta do WSL virar a tela preta da máquina bia-dev.
