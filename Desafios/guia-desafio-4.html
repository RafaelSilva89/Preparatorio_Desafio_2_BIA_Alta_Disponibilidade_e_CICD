O que o desafio pede, e o que já existe

O enunciado tem quatro linhas. Elas parecem quatro tarefas soltas, mas são uma coisa só: montar um bastion host descartável — uma máquina sem porta aberta, ligada só quando você precisa, que serve de ponte entre o seu notebook e recursos privados da AWS.

Por que "porteiro"

O nome técnico é bastion host: uma máquina que não hospeda nada e existe só para ser o ponto de entrada controlado de uma rede privada. Ela não tem porta aberta para a internet, não tem chave SSH, e só responde a quem tem permissão de SSM na sua conta AWS.

A vantagem prática aparece no dia da demissão: tirar a permissão de SSM de um usuário no IAM derruba o acesso dele na hora — sem trocar senha de banco, sem revogar chave, sem mexer em Security Group.

$ sudo apt-get update
$ sudo apt-get install -y postgresql-client
$ psql --version

É postgresql-client, e não postgresql: você quer o cliente que conecta em um banco remoto, não um servidor PostgreSQL rodando dentro do WSL.

O <<'FIM' com aspas tem um motivo

É um here-document: tudo entre a primeira linha e o FIM vai para dentro do arquivo. 1.3

Religar a EC2 do cluster e a task da API

WSL

Duas camadas, nesta ordem: primeiro o Auto Scaling Group devolve a máquina, depois o serviço do ECS recoloca a task nela. Inverter a ordem só faz o ECS ficar esperando capacidade que ainda não existe.

1. Devolver a capacidade ao Auto Scaling
$ ASG=$(aws autoscaling describe-auto-scaling-groups \
  --query "AutoScalingGroups[?contains(AutoScalingGroupName, 'cluster-bia')].AutoScalingGroupName" \
  --output text)
$ echo "$ASG"
$ aws autoscaling update-auto-scaling-group \
  --auto-scaling-group-name "$ASG" --min-size 1 --max-size 1 --desired-capacity 1
Resposta esperada
Infra-ECS-Cluster-cluster-bia-xxxxxxxx-ECSAutoScalingGroup-xxxxxxxxxxxx

O update-auto-scaling-group não imprime nada quando dá certo — o silêncio é a resposta boa. A instância nova leva de 2 a 4 minutos para subir e se registrar no cluster.

Max bound, 0, must be greater than or equal to min bound, 1

Aparece quando a pausa do Desafio 3 zerou também o máximo do ASG. Sem o --max-size 1 o comando falha, nenhuma EC2 sobe e o serviço fica para sempre em Rodando 0. Confira os três valores com:

aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names "$ASG" \
  --query 'AutoScalingGroups[0].{Min:MinSize,Max:MaxSize,Desejado:DesiredCapacity,Instancias:length(Instances)}' --output table
2. Devolver a task ao serviço
$ aws ecs update-service --cluster "$ECS_CLUSTER" --service "$ECS_SERVICE" \
  --desired-count 1 --query 'service.{Servico:serviceName,Desejado:desiredCount}' --output table
3. Esperar a task ficar RUNNING
$ aws ecs describe-services --cluster "$ECS_CLUSTER" --services "$ECS_SERVICE" \
  --query 'services[0].{Desejado:desiredCount,Rodando:runningCount,Status:status}' --output table
Resposta esperada
-------------------------------------
|          DescribeServices         |
+-----------+-----------+-----------+
| Desejado  |  Rodando  |  Status   |
+-----------+-----------+-----------+
|  1        |  1        |  ACTIVE   |
+-----------+-----------+-----------+

Enquanto Rodando for 0, repita o comando. Se ele travar em 0 por mais de cinco minutos, a causa quase sempre é a instância do ASG ainda não ter aparecido — confira com o describe-instances do passo 1.1 e com aws ecs describe-clusters --clusters "$ECS_CLUSTER" --query 'clusters[0].registeredContainerInstancesCount' (deve ser 1). Se a instância já está registrada e mesmo assim nada roda, aws ecs describe-services --cluster "$ECS_CLUSTER" --services "$ECS_SERVICE" --query 'services[0].events[:5].message' diz o motivo.

O que vale é o hostPort

São dois números diferentes e confundi-los faz o túnel abrir e não responder nada. O containerPort (8080) é a porta dentro do contêiner. O hostPort (80) é a porta na máquina — e é nela que o porteiro vai bater. É esse número que vai para o BIA_PORT.

Se a sua saída mostrar hostPort 3001, use 3001. O guia usa 80 porque é o que esta task definition publica.

Os quatro ingredientes para lançar uma EC2

Antes de escrever o script, descubra à mão o que ele vai descobrir sozinho. Dois filtros, um E lógico

Comando
$ cat > 01-lancar-porteiro-zona-b.sh <<'FIM'
#!/usr/bin/env bash
# Lanca a EC2 "porteiro" na subnet default da zona informada.
# Uso: ./01-lancar-porteiro-zona-b.sh <nome> [zona] [tipo]
# O profile vem do ambiente (export AWS_PROFILE), nao do codigo.

NOME=$1
ZONA=${2:-us-east-1b}
TIPO=${3:-t3.micro}
PERFIL_SSM=role-acesso-ssm
SG_NOME=bia-porteiro

if [ -z "$NOME" ]; then
    echo "Uso: $0 <nome-do-porteiro> [zona] [tipo]"
    exit 1
fi

# 1. ja existe uma instancia com esse nome? entao nao lance outra.
EXISTENTE=$(aws ec2 describe-instances \
    --filters "Name=tag:Name,Values=$NOME" \
              "Name=instance-state-name,Values=pending,running,stopping,stopped" \
    --query "Reservations[].Instances[].InstanceId[]" \
    --output text)

if [ -n "$EXISTENTE" ]; then
    echo "Porteiro ja existe: $EXISTENTE - nada a fazer"
    exit 0
fi

# 2. a subnet default da zona pedida
SUBNET_ID=$(aws ec2 describe-subnets \
    --filters "Name=default-for-az,Values=true" "Name=availability-zone,Values=$ZONA" \
    --query "Subnets[0].SubnetId" --output text)

if [ -z "$SUBNET_ID" ] || [ "$SUBNET_ID" = "None" ]; then
    echo "Subnet default da zona $ZONA nao encontrada"
    exit 1
fi

VPC_ID=$(aws ec2 describe-subnets --subnet-ids "$SUBNET_ID" \
    --query "Subnets[0].VpcId" --output text)

# 3. a AMI mais recente do Amazon Linux 2023, direto do parametro publico
AMI_ID=$(aws ssm get-parameters \
    --names /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \
    --query "Parameters[0].Value" --output text)

if [ -z "$AMI_ID" ] || [ "$AMI_ID" = "None" ]; then
    echo "AMI do Amazon Linux 2023 nao encontrada"
    exit 1
fi

# 4. o security group do porteiro: criado sem regra de entrada, de proposito
SG_ID=$(aws ec2 describe-security-groups \
    --filters "Name=group-name,Values=$SG_NOME" "Name=vpc-id,Values=$VPC_ID" \
    --query "SecurityGroups[0].GroupId" --output text)

if [ -z "$SG_ID" ] || [ "$SG_ID" = "None" ]; then
    echo "Criando o security group $SG_NOME"
    SG_ID=$(aws ec2 create-security-group \
        --group-name "$SG_NOME" \
        --description "EC2 porteiro - entrada apenas por SSM" \
        --vpc-id "$VPC_ID" \
        --query "GroupId" --output text)

    if [ -z "$SG_ID" ]; then
        echo "Falha ao criar o security group $SG_NOME"
        exit 1
    fi
fi

echo "Zona:   $ZONA"
echo "Subnet: $SUBNET_ID (VPC $VPC_ID)"
echo "AMI:    $AMI_ID"
echo "SG:     $SG_ID"

# 5. lancar a instancia
INSTANCE_ID=$(aws ec2 run-instances \
    --image-id "$AMI_ID" \
    --instance-type "$TIPO" \
    --subnet-id "$SUBNET_ID" \
    --security-group-ids "$SG_ID" \
    --iam-instance-profile Name=$PERFIL_SSM \
    --metadata-options "HttpTokens=required,HttpEndpoint=enabled" \
    --tag-specifications "ResourceType=instance,Tags=[{Key=Name,Value=$NOME}]" \
    --query "Instances[0].InstanceId" --output text)

if [ -z "$INSTANCE_ID" ]; then
    echo "Falha ao lancar a instancia"
    exit 1
fi

echo "Porteiro lancado: $INSTANCE_ID"
echo "Aguardando o estado running..."
aws ec2 wait instance-running --instance-ids "$INSTANCE_ID"
echo "Pronto: $NOME esta running na zona $ZONA"
FIM

Comando
$ cat > 02-iniciar-porteiro-tunel-rds.sh <<'FIM'
#!/usr/bin/env bash
# Liga o porteiro (se preciso) e abre o tunel SSM ate o RDS.
# Uso: ./02-iniciar-porteiro-tunel-rds.sh <nome-do-porteiro> <id-do-rds> [porta-local]

NOME=$1
NOME_RDS=$2
PORTA_LOCAL=${3:-5433}

if [ -z "$NOME" ] || [ -z "$NOME_RDS" ]; then
    echo "Uso: $0 <nome-do-porteiro> <id-do-rds> [porta-local]"
    exit 1
fi

# 1. achar o porteiro em qualquer estado - inclusive desligado
INSTANCE_ID=$(aws ec2 describe-instances \
    --filters "Name=tag:Name,Values=$NOME" \
              "Name=instance-state-name,Values=pending,running,stopping,stopped" \
    --query "Reservations[].Instances[].InstanceId[]" \
    --output text)

if [ -z "$INSTANCE_ID" ]; then
    echo "Porteiro '$NOME' nao encontrado"
    exit 1
fi
echo "Porteiro encontrado: $INSTANCE_ID"

# 2. ligar, se estiver parado
ESTADO=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
    --query "Reservations[].Instances[].State.Name" --output text)

if [ "$ESTADO" != "running" ]; then
    echo "Porteiro esta '$ESTADO' - ligando"
    aws ec2 start-instances --instance-ids "$INSTANCE_ID" > /dev/null
    aws ec2 wait instance-running --instance-ids "$INSTANCE_ID"
fi

# 3. esperar o agente do SSM responder, no maximo 5 minutos
echo "Aguardando o agente do SSM..."
PING=""
for _ in $(seq 1 30); do
    PING=$(aws ssm describe-instance-information \
        --filters "Key=InstanceIds,Values=$INSTANCE_ID" \
        --query "InstanceInformationList[0].PingStatus" --output text)
    [ "$PING" = "Online" ] && break
    sleep 10
done

if [ "$PING" != "Online" ]; then
    echo "O agente do SSM nao ficou Online a tempo"
    exit 1
fi
echo "SSM: Online"

# 4. descobrir o endereco do banco
ENDPOINT_RDS=$(aws rds describe-db-instances --db-instance-identifier "$NOME_RDS" \
    --query "DBInstances[0].Endpoint.Address" --output text)

if [ -z "$ENDPOINT_RDS" ] || [ "$ENDPOINT_RDS" = "None" ]; then
    echo "RDS '$NOME_RDS' nao localizado"
    exit 1
fi

echo "Endpoint do RDS: $ENDPOINT_RDS"
echo "Tunel: localhost:$PORTA_LOCAL --> $ENDPOINT_RDS:5432"
echo "Deixe este terminal aberto. Ctrl+C encerra o tunel."

# 5. abrir o encaminhamento de porta
aws ssm start-session --target "$INSTANCE_ID" \
    --document-name AWS-StartPortForwardingSessionToRemoteHost \
    --parameters "{\"host\":[\"$ENDPOINT_RDS\"],\"portNumber\":[\"5432\"],\"localPortNumber\":[\"$PORTA_LOCAL\"]}"

As três novidades deste script

A base é a mesma da Fase 3. Vale olhar só o que mudou.

O trechoO que fazPor que está aí

De onde vem: o 06-2-parar-porteiro.sh da aula

A lógica é a mesma — achar a máquina pelo nome e parar se estiver ligada. O que muda:

  • Filtra os estados pending,running,stopping,stopped no servidor, em vez de pegar tudo e passar por grep running.

Comando

#!/usr/bin/env bash
# Para a EC2 do porteiro, se ela estiver ligada.
# Uso: ./04-parar-porteiro.sh <nome-do-porteiro>

NOME=$1

if [ -z "$NOME" ]; then
    echo "Uso: $0 <nome-do-porteiro>"
    exit 1
fi

# achar em qualquer estado: parar uma maquina ja parada nao pode ser um erro
INSTANCE_ID=$(aws ec2 describe-instances \
    --filters "Name=tag:Name,Values=$NOME" \
              "Name=instance-state-name,Values=pending,running,stopping,stopped" \
    --query "Reservations[].Instances[].InstanceId[]" \
    --output text)

if [ -z "$INSTANCE_ID" ]; then
    echo "Porteiro '$NOME' nao encontrado"
    exit 1
fi

ESTADO=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" \
    --query "Reservations[].Instances[].State.Name" --output text)

if [ "$ESTADO" != "running" ]; then
    echo "Porteiro $INSTANCE_ID ja esta '$ESTADO' - nada a fazer"
    exit 0
fi

echo "Parando o porteiro $INSTANCE_ID"
aws ec2 stop-instances --instance-ids "$INSTANCE_ID" > /dev/null
aws ec2 wait instance-stopped --instance-ids "$INSTANCE_ID"
echo "Porteiro $NOME parado"
FIM
$ chmod +x 04-parar-porteiro.sh
Duas diferenças em relação ao 06-2-parar-porteiro.sh da aula

1. A aula usa grep running na saída e compara com ==, que não é sintaxe de [ ] em shell POSIX — funciona no Bash e quebra em sh. Aqui a comparação é != com um único =, e o estado vem direto do --query, sem grep.

2. A aula manda o stop-instances para segundo plano com & e imprime "já está sendo parado". Aqui o wait instance-stopped segura até a máquina realmente parar — assim o script só termina quando a cobrança de fato acabou, e você pode encadeá-lo com outros comandos.
