O que o desafio pede e como ler este guia

A ideia central: a aplicação não muda. O que muda é a infraestrutura embaixo dela. O contrato container → porta → banco é idêntico no notebook e na nuvem — e é por isso que a Parte 2 é curta: ela repete, com serviços gerenciados, o que a Parte 1 já provou funcionar.

A leitura que o diagrama entrega

Ambiente de referência

O WSL 2, o Ubuntu e o Git são instalados durante o roteiro (passos 2 e 4). Este laboratório foi executado num notebook modesto — Dell Inspiron 14 3000, Core i3-4005U de 2 núcleos, 8 GB de RAM, Windows 11 Pro 24H2 — com WSL 2.7.11, Ubuntu 24.04.4 LTS, Git 2.43, Docker Desktop 4.86 e Compose v5.3.1. Se a sua máquina for mais forte, tudo aqui continua valendo; você só terá mais folga.

Por que WSL 2 e não uma máquina virtual

A instrução original do curso sugere montar uma VM. Com 8 GB de RAM e um i3 de 2 núcleos, isso significaria manter dois sistemas operacionais disputando a mesma memória:

 VirtualBox                            WSL 2
 Windows                               Windows
   +-- VM Ubuntu (SO completo)           +-- Ubuntu (kernel compartilhado)
         +-- Docker Engine                     +-- Docker CLI
                                                     +-- Docker Desktop (engine unico)

O caminho escolhido foi o WSL 2 com os recursos limitados de propósito (passo 3), deixando ~5 GB para Windows, navegador, VS Code e Docker Desktop. O resultado é um Linux real, com Docker nativo, que não derruba a máquina hospedeira.

O mesmo raciocínio vale para o Docker: não instale docker.io dentro do Ubuntu. O Docker Desktop já fornece o engine, e a integração com o WSL apenas expõe a CLI dentro da distribuição — um daemon, não dois.

Como ler as etiquetas de cada passo

POWERSHELL = terminal do Windows · WSL = Ubuntu dentro do Windows · APP = interface gráfica (Docker Desktop, VS Code, DBeaver) · CONSOLE = navegador, no Console da AWS · CLOUDSHELL = terminal do CloudShell · BIA-DEV = dentro da EC2, pela sessão do SSM.

O prompt à esquerda do comando diz a mesma coisa, e é o sinal mais confiável de onde você está:

  PS>                   -->  PowerShell, no Windows
  $                     -->  WSL, o Ubuntu dentro do seu Windows
  [cloudshell]$         -->  CloudShell, no navegador
  [root@ip-... ~]#      -->  dentro da EC2, pela sessao do SSM

3

Limitar os recursos do WSL

POWERSHELL

Dizer ao WSL quanta memória e CPU ele pode consumir. Por padrão ele toma bem mais do que um notebook de 8 GB pode ceder — este é o passo que torna o laboratório viável.

Abrir o arquivo (vem vazio)
PS> notepad "$env:USERPROFILE\.wslconfig"
Colar exatamente isto e salvar
[wsl2]
memory=3GB
processors=2
swap=1GB
localhostForwarding=true

[experimental]
autoMemoryReclaim=gradual
ParâmetroEfeito
memory=3GBTeto de RAM do WSL — impede que o Ubuntu sufoque o Windows
processors=22 das 4 threads para o WSL, mantendo o host responsivo
swap=1GBProteção contra estouro de memória (mais lento que RAM, mas evita travar)
localhostForwarding=trueEssencial aqui: faz localhost:3001 do Windows chegar no container dentro do WSL
autoMemoryReclaim=gradualDevolve ao Windows a memória que o WSL deixou de usar
localhostForwarding=true é a linha que o desafio inteiro depende

Sem ela o container sobe normalmente dentro do WSL, mas http://localhost:3001 não abre no navegador do Windows — e o passo 9 parece um problema de aplicação quando é de rede.

O arquivo só passa a valer depois de reiniciar o WSL por completo:

Aplicar
PS> wsl --shutdown
PS> wsl -d Ubuntu-24.04
Conferir dentro do Ubuntu
$ free -h    # esperado: ~3.0Gi em Mem e 1.0Gi em Swap
$ nproc      # esperado: 2
Resposta esperada

Subir o projeto BIA

WSL

Clonar a aplicação e subir os três containers de uma vez: aplicação, banco e cache. É o compose.yml do projeto que descreve os três e a rede entre eles.

Comando
$ cd ~/laboratorios-aws
$ git clone https://github.com/henrylle/bia
$ cd bia
$ docker compose up -d
Na primeira vez isso demora — e é normal

O serviço server é definido com build: ., então o Docker baixa a imagem do Node 24 e compila o front-end antes de subir. Em um i3 são vários minutos.

Acompanhe o progresso com docker compose logs -f server (saia com Ctrl+C — isso encerra o log, não o container).

Validar
$ docker compose ps
Resposta esperada (saída resumida)
NAME       IMAGE                      SERVICE    STATUS          PORTS
bia        bia-server                 server     Up 9 seconds    0.0.0.0:3001->8080/tcp
database   postgres:17.1              database   Up 12 seconds   0.0.0.0:5433->5432/tcp
redis      valkey/valkey:8.1-alpine   redis      Up 12 seconds   0.0.0.0:6379->6379/tcp

O comando real também traz as colunas COMMAND e CREATED, e repete cada porta na forma IPv6 [::]:3001->8080/tcp. Para validar sem abrir o navegador, a API responde a versão:

A API responde
$ curl http://localhost:3001/api/versao
Resposta esperada
Bia 4.3.0

Abra http://localhost:3001 no navegador do Windows — graças ao localhostForwarding=true do passo 3, a porta publicada dentro do WSL responde direto no host.

Entendendo o mapeamento de portas

Este é o conceito que separa "copiei o comando" de "entendi a rede". Em 3001:8080, o número da esquerda é o host e o da direita é o container.

  Windows            WSL / Docker                    dentro da rede do Docker

  navegador  --->  0.0.0.0:3001  --->  server:8080  --->  database:5432
                                                            ^
  DBeaver    --->  0.0.0.0:5433  ------------------------- +
                                        (a aplicacao NUNCA passa pela 5433)

A aplicação não usa a porta 5433. O container server fala com o database pela rede interna do Docker, na porta nativa 5432, resolvendo o nome do serviço (DB_HOST=database).

A 5433 existe apenas para o DBeaver acessar o banco de fora — e foi escolhida justamente para não colidir com uma eventual instalação de PostgreSQL no Windows.

Rodar as migrations do banco

WSL

Criar as tabelas da aplicação. O container do PostgreSQL sobe com o banco bia vazio — as tabelas são criadas por um comando à parte.

Esta etapa não é opcional

Sem ela a tabela Tarefas não existe e o cadastro na tela falha — justamente o teste que o desafio pede para comprovar a persistência. É um erro que parece de código, mas é de dados: container de banco no ar não significa schema criado.

Comando

Resposta esperada

Loaded configuration file "config/database.js".

Rodou duas vezes?

A resposta vira No migrations were executed, database schema was already up to date. — sinal de que o banco já está no estado correto, e não de erro.

Prova de execução — as tabelas passam a existir
$ docker compose exec database psql -U postgres -d bia -c '\dt'

Tarefas guarda os dados da aplicação; SequelizeMeta é o controle interno de quais migrations já rodaram — é ela que faz a segunda execução do comando não repetir nada.

12

Provar a persistência dos dados

WSL

O teste central do desafio: derrubar todo o ambiente e comprovar que os dados continuam existindo. Isso funciona porque o PostgreSQL grava em um volume nomeado, que tem vida independente do container.

Onde os dados realmente moram
$ docker volume ls | grep bia
Resposta esperada
local     bia_db
O teste, em quatro passos
# 1. Confirme que existe uma tarefa cadastrada em http://localhost:3001

# 2. Derrube os containers (o volume permanece)
$ docker compose down

# 3. Suba tudo de novo
$ docker compose up -d

# 4. Abra http://localhost:3001 novamente
O que o down remove — containers e rede, nenhum volume
 Container bia Removed
 Container redis Removed
 Container database Removed
 Network bia_default Removing
 Network bia_default Removed

A tarefa cadastrada antes do down continua na tela — e você não precisou rodar as migrations de novo. Para conferir direto no banco, sem abrir o navegador:

Conferir no banco
$ docker compose exec database psql -U postgres -d bia -c 'SELECT titulo, dia_atividade FROM "Tarefas";'
Resposta esperada — o mesmo registro de antes do down
           titulo           | dia_atividade
----------------------------+---------------
 Testando o acesso ao banco | 12/08/2026
(1 row)

Mesmo uuid, mesma data de criação. O container foi destruído e recriado; o dado não.

As aspas duplas em "Tarefas" são obrigatórias

O Sequelize cria a tabela com T maiúsculo, e o PostgreSQL só preserva maiúsculas em identificadores entre aspas. Sem elas o comando falha com relation "tarefas" does not exist — que parece tabela inexistente e é só maiúscula perdida.

A diferença que importa

docker compose down → remove containers e rede. Os volumes — e os dados — permanecem.

docker compose down -v → remove também os volumes. Apaga o banco inteiro, e depois disso é preciso repetir o passo 10 (migrations) do zero.

Criar os Security Groups

CONSOLE

Criar as regras de firewall antes da máquina existir. Um Security Group é uma lista do que pode entrar; tudo que não está liberado é bloqueado.

1. EC2 -> Security Groups -> Create security group
2. Name: bia-dev | Description: Acesso a aplicacao BIA na porta 3001 | VPC: a default
3. Inbound rules -> Add rule: Type "Custom TCP", Port 3001, Source "Anywhere-IPv4"
4. Create security group
5. Repita para o bia-db: Type "PostgreSQL", Port 5432, e em Source escolha
   "Custom" e selecione o Security Group bia-dev na lista
Mesmo passo pelo CloudShell (AWS CLI)
Comando
# Descobrir a VPC padrao
[cloudshell]$ VPC_ID=$(aws ec2 describe-vpcs --filters Name=isDefault,Values=true \
  --query 'Vpcs[0].VpcId' --output text)

# Security Group da aplicacao
[cloudshell]$ SG_APP=$(aws ec2 create-security-group \
  --group-name bia-dev \

[cloudshell]$ aws ec2 authorize-security-group-ingress \

[cloudshell]$ SG_DB=$(aws ec2 create-security-group \

  --vpc-id "$VPC_ID" --query 'GroupId' --output text)

[cloudshell]$ aws ec2 authorize-security-group-ingress \
  --group-id "$SG_DB" --protocol tcp --port 5432 --source-group "$SG_APP"

[cloudshell]$ echo "SG_APP=$SG_APP"
[cloudshell]$ echo "SG_DB=$SG_DB"

sg-xxxxxxxxxxxxxxxxx

Significa que o banco foi aberto para a internet e precisa ser corrigido. A entrada do bia-db tem que mostrar o ID do grupo bia-dev como origem, e não um bloco de IPs.

Por que o banco não fica aberto para a internet

Porque ele não precisa. Só a aplicação conversa com ele. Apontar a origem para outro Security Group significa "qualquer máquina que pertença ao grupo bia-dev pode entrar" — mesmo que o IP dela mude.

O ajuste obrigatório antes de construir a imagem

Este é o erro mais comum de quem chega até aqui: a página abre normalmente, mas o formulário não salva nada.

O motivo é que o Dockerfile da BIA compila o React com VITE_API_URL=http://localhost:3001 — e localhost, no navegador de quem acessa, é o computador dele, não a EC2.

3 · Trocar a URL da API pelo IP público da instância
[root@ip ~]# IP_PUBLICO=$(curl -s http://169.254.169.254/latest/meta-data/public-ipv4)
[root@ip ~]# echo "IP publico da instancia: $IP_PUBLICO"

[root@ip ~]# sed -i "s|VITE_API_URL=http://localhost:3001|VITE_API_URL=http://$IP_PUBLICO:3001|" Dockerfile
[root@ip ~]# grep VITE_API_URL Dockerfile    # conferir que o IP entrou
Resposta esperada — o IP no lugar de localhost
ENV VITE_API_URL=http://xx.xx.xx.xx:3001
4, 5 e 6 · Construir, subir apontando para o RDS e criar as tabelas
# 4. Construir a imagem
[root@ip ~]# docker build -t bia:latest .

# 5. Subir o container com as variaveis do RDS
[root@ip ~]# docker run -d --name bia --restart unless-stopped -p 3001:8080 \
  -e DB_HOST='<ENDPOINT-DO-RDS>' \
  -e DB_PORT=5432 \
  -e DB_USER=postgres \
  -e DB_PWD='<SENHA-DO-RDS>' \
  bia:latest

# 6. Criar as tabelas no RDS (o mesmo passo 10, agora na nuvem)
[root@ip ~]# docker exec bia bash -c 'npx sequelize db:migrate'
DB_PORT=5432 é obrigatório

Se a variável não for informada, a aplicação assume 5433 — o valor do ambiente local — e a conexão com o RDS falha por timeout, sem mensagem de erro útil.

Sobre SSL: não precisa configurar nada

A aplicação detecta que o DB_HOST não é localhost nem database e liga o SSL automaticamente — que é o que o RDS exige por padrão.
